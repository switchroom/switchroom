# pg_search BM25 filter-field pushdown — evidence

Epic [#4474](https://github.com/switchroom/switchroom/issues/4474) phase P4,
issue [#4478](https://github.com/switchroom/switchroom/issues/4478).
Captured 2026-08-07, Australia/Melbourne.

## What was wrong

The ParadeDB BM25 index the engine builds covers `(id, text, context,
text_signals)` and nothing else. Every recall keyword arm
(`engine/sql/postgresql.py` `build_bm25_arm`, the `pg_search` branch) filters
on:

```sql
WHERE bank_id = $n AND fact_type = '<literal>' AND id @@@ paradedb.boolean(...)
```

Because `bank_id` and `fact_type` are not indexed, ParadeDB cannot push those
equalities into the Tantivy scan. It degrades them to a **post-scoring
`heap_filter`** inside the custom scan — visible in the plan's `Tantivy Query`
as `"field_filters":[{"heap_filter":"(bank_id = 'bank-01'::text)"}]`. The arm
therefore scores the **whole table**, then throws away everything outside the
bank.

The results are byte-identical either way (see AC6). Nothing but a query plan
or a latency chart can see this defect, which is why it survived.

## The fix

Append the two columns to the index with the **`literal`** tokenizer:

```sql
CREATE INDEX idx_memory_units_text_search ON memory_units
  USING bm25 (id, text, context, text_signals,
              (bank_id::pdb.literal), (fact_type::pdb.literal))
  WITH (key_field='id');
```

Nothing in the query changes. ParadeDB absorbs the plain SQL `WHERE`
automatically once the columns carry the `literal` tokenizer, so
`engine/sql/postgresql.py` is deliberately **not** patched — see
"Correction to the issue's plan" below.

The tokenizer choice is load-bearing and is hard-coded, never taken from
`HINDSIGHT_API_TEXT_SEARCH_EXTENSION_PG_SEARCH_TOKENIZER`: equality pushdown
requires the whole column value to be a single token, so a stemmed / ngram /
lindera cast on a filter column would stop the predicate matching **at all** —
empty keyword recall, not merely slow keyword recall.

Shipped as a build-time patch in `docker/Dockerfile.hindsight` (no engine
source is edited), guarded behaviourally by
`tests/docker/hindsight-pg-search-filter-pushdown-patch.test.ts` and
structurally by `tests/docker/dockerfile-hindsight-bakes.test.ts`.

## Correction to the issue's plan

#4478 scope item 2 asked to fold `bank_id`/`fact_type` into the `@@@`
expression via `paradedb.boolean(must => ...)`. That turned out to be
**unnecessary**: the plans below were captured with the query completely
unchanged, and the corrected index alone moves both predicates from
`heap_filter` into `must` as `term` clauses. Rewriting the arm would have been
churn against zero measured benefit, so it was not done.

## Method

Everything was measured in a **throwaway sandbox container**, never against the
live fleet. The live database was read only for anonymised aggregates.

- ParadeDB `pg_search` 0.25.1 in the pinned hindsight image, embedded
  PostgreSQL 18.1, 4 CPUs / 10 GB.
- Synthetic corpus: 797,893 rows over 14 banks, generated by
  `repro/gen.py` (seed `20260807`). Bank sizes mirror the live
  `memory_units` distribution under **anonymous labels** (`bank-01` largest at
  232,382 rows … `bank-14` smallest at 12); `fact_type` mix 60.9 / 20.3 / 18.8
  world / experience / observation. Vocabulary is 20,000 Zipf-weighted
  synthetic tokens (`tk00000`…`tk19999`) — no real memory text was copied.
- `repro/bench.py` mirrors `build_bm25_arm` exactly: a `UNION ALL` of one arm
  per `fact_type`, `ORDER BY score DESC LIMIT 50`. Nearest-rank percentiles,
  3s warm-up, 15s per cell, backends **interleaved within each cell**.

### Contention disclosure — read before quoting any latency number

Both sweeps ran while epic phase P2 (#4476) was loading the same box and GPU
(host load 6-11 on 16 cores). This was unavoidable — the two phases were
dispatched in parallel — and it is disclosed rather than hidden:

- **Absolute milliseconds do not transfer to the live fleet.** The `native`
  comparator drifted 22% between the two sweeps on the same unchanged
  configuration (bank-01, concurrency 1: 138.9 ms vs 113.9 ms p95). Treat every
  absolute figure here as sandbox-under-load.
- **The comparison IS robust.** Backends were interleaved within each cell, so
  contention hits both arms of every comparison equally, and the corrected /
  uncorrected gaps below are 6-10x — an order of magnitude larger than the
  observed drift.
- Concurrency 8 and 16 are queue-bound by the 4-CPU quota; read them as
  "behaviour under saturation", not as a fleet capacity model.
- The `EXPLAIN` buffer counts are **not** latency and are unaffected by
  contention. They are the primary evidence.

## AC1 — filter pushdown, proven (PASS)

Full plans: `explain-uncorrected.txt`, `explain-corrected.txt`. Same query,
same data, same session settings; only the index differs.

| | uncorrected | corrected |
|---|---|---|
| `bank_id` predicate | `"field_filters":[{"heap_filter":"(bank_id = 'bank-01'::text)"}]` | `{"term":{"field":"bank_id","value":"bank-01"}}` inside `must` |
| `fact_type` predicate | `heap_filter` | `{"term":{"field":"fact_type","value":"world"}}` inside `must` |
| `heap_filter` count | 2 | 0 |

## AC2 — scan amplification, via buffers (PASS, restated)

The AC as written asked for `Rows Removed by Filter` to fall. ParadeDB 0.25
does not emit that line for this plan shape: `TopKScanExecState` only heap-
fetches the final N, so `Heap Fetches: 50` in **both** runs. The amplification
is real and shows in the buffer counters instead:

| | uncorrected | corrected |
|---|---|---|
| `Buffers: shared hit` (scan node) | 171,517 | 405 |
| Execution time | 231.4 ms | 7.8 ms |

**423x fewer buffer hits** for an identical result set.

### This replaces the recorded "pg_search is a 124-138 ms regression" claim

The **uncorrected** index is 2-10x slower than native at saturation (bank-01,
concurrency 16: 1008 ms vs 708 ms p95). That reproduces the regression the epic
recorded and explains it: those numbers measured the missing fast fields, not
pg_search. Corrected, the same backend is 4-6x **faster** than native at every
cell.

## AC6 — results are unchanged (PASS)

120 queries × 3 fact_type arms, corrected vs uncorrected, compared row by row
(4,362 rows total):

- 0 rows present only in the uncorrected result
- 0 rows present only in the corrected result
- 0 BM25 score mismatches
- 0 rank mismatches

The filter **moved**; it did not narrow. This is what makes the defect
invisible without a plan, and what makes the fix safe.

## Rollout — read this before assuming the fleet is fixed

A **fresh** database gets the corrected index from the initial-schema
migration. An **existing** database does not, and the fix is deliberately not
self-applying:

- Upstream's boot-path detector (`migrations.py`) keys on the `key_field`
  reloption alone and never inspects the column list, so a live uncorrected
  index is adopted as correct.
- Rebuilding it on the every-boot path means `DROP INDEX` + `CREATE INDEX` on a
  populated table, which is exactly the window where the pg_search arm raises
  `XX000 ... does not contain a USING bm25 index` — epic #4474 finding C2.
  Turning a performance gap into an availability gap on the boot path is worse
  than reporting it.

So an existing instance logs the gap loudly on every boot
(`pg_search_filter_field_drift ... missing=['bank_id', 'fact_type']`) and waits
for a deliberate, scheduled rebuild:

```sql
DROP INDEX CONCURRENTLY idx_memory_units_text_search;
CREATE INDEX CONCURRENTLY idx_memory_units_text_search ON memory_units
  USING bm25 (id, text, context, text_signals,
              (bank_id::pdb.literal), (fact_type::pdb.literal))
  WITH (key_field='id');
```

Copy the **text** column casts from the live `pg_indexes.indexdef` verbatim
rather than from the snippet above — an instance running with
`HINDSIGHT_API_TEXT_SEARCH_EXTENSION_PG_SEARCH_TOKENIZER` set carries e.g.
`(text::pdb.simple('stemmer=english'))`, and retyping them uncast would silently
downgrade the analyzer. Only the two `pdb.literal` filter columns are new.

Keyword recall degrades to semantic-only between the two statements — the
fail-closed fallback from #4472 covers that window rather than erroring.
